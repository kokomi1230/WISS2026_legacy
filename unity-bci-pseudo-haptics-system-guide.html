unity-bci-pseudo-haptics / システム解説

システム構成と設定パラメータ・使い方

脳波デコーダから届く分類結果で仮想の手を動かし、試行を回して記録する Unity プロジェクトの全体像をまとめる。第 1 部で構成と信号の流れ、第 2 部で設定パラメータの置き場所と一覧、第 3 部で実験の回し方と記録・検証の手順を扱う。2 つのシーンは別の実験である（把握の想起と、腕の持ち上げの想起）。発火の判定は Unity 側にあり、閾値と連続 N 回は設定 asset から振れる。実験デザインの根拠は別資料「MRCP 想起オンセット同期システムの説明と実験プロトコル」にある。

第1部

システム

SECTION 1

何をするシステムか

脳波から被験者の運動想起を読み取り、その結果で一人称の仮想の手を動かす。Unity 側の役割は、キューを出し、届いた推定から発火を判定して手を動かし、時刻を記録することの 3 つである。

脳波の計測とデコードは別プロジェクトの python-bci-platform が受け持つ。本リポジトリは UDP でつながる受信側と提示側であり、脳波そのものには触れない。

要点

発火の判定は Unity 側にある。python 側は一定レートで「いま何を推定しているか」を流すだけで、いつ手を動かすかは決めない。確信度の閾値と連続 N 回の成立条件は Unity の設定 asset にあり、実験者がその場で振れる。

2 つのシーンは別の実験である

被験者が想起する内容も、検証したいことも違う。共通なのは UDP でデコーダと話す部分と手の駆動だけである。

HandExperimentPseudoHapticsExperiment
被験者が行う想起把握腕の持ち上げ
発火で起きること手が閉じる掴んだ物体ごと腕が上がる
把持の扱い検証対象そのもの前提条件（BCI モード入りで既に握っている）
C/D 比使わない持ち上げ変位に掛ける（検証対象）
手首BCI 駆動中は凍結するトラッキングを続ける
測るものキューからの発火誤差 Δt と主観的一致度持ち上げ距離と重さの知覚
Settings assetHandExperimentSettings のみPseudoHapticsSettings のみ
試行タイムラインある（ExperimentRunner が回す）無い

疑似触覚（C/D 比）とは

Control / Display 比。実際の指令に対して、画面上の手をわざと違う量だけ動かす。物を持ち上げるときに指令より仮想の手が遅れて付いてくると、人はその物を「重い」と感じる。触覚提示装置を使わずに重さの知覚を作る手法である（Samad et al., CHI 2019）。

本システムでは持ち上げの指令変位に掛ける。指令の出どころは BCI でもデバッグキーでも同じ経路を通るため、C/D 比の効き方は変わらない。

補足

環境は Unity 6000.4.8f1、URP 17.4、XR Hands 1.8、XR Interaction Toolkit 3.4、Animation Rigging 1.4。スクリプトのアセンブリは PseudoHaptics の 1 つで、名前空間も同名である。

SECTION 2

信号の流れと実行順

脳波が計測器から出て手が動くまでを 8 段に分けられる。Unity が受け持つのは 5 段目から 8 段目である。発火判定が Unity 側にあるのが以前の設計との違いである。

取得python / LSL → フィルタpython → 推論shrinkage LDA → UDP 送信ポート 5001 へ → 受信UdpPacketReceiver → 発火判定連続 N 回・Unity 側 → 開閉の速度制限GraspLevelController → 描画HandGraspAnimator / BciLiftDriver

「開閉の速度制限」とは（旧称: 平滑化）

信号のノイズ除去ではない。GraspLevelSmoother は把持レベルを 0 から 1 へ closeSeconds かけて線形に動かすだけの、開閉アニメーションの速度制限である。

これが無いと手は 1 フレームで握り込み、grasp_reach_unix（把持到達時刻）も測れない。また、0/1 の硬い分類を出すデコーダと連続的な確信度を出すデコーダのどちらを繋いでも、手の見た目の動きが同じになる。以前の資料が「平滑化」と呼んでいたのはこの処理であり、ノイズ対策ではないので名前を改めた。

Unity 側のコンポーネント

1 フレーム内の処理順は DefaultExecutionOrder で固定してある。受信が最も早く、記録とリグ評価が最も遅い。

BciLiftDriver（220）は HandRootDriver（0）と Grabbable（250）のあいだになければならない。HandRootDriver は毎フレーム手首へ生のトラッキング姿勢を書き込むので、前フレームのオフセットはそこで消える。

これを Grabbable より後ろへ置くと、物体はオフセットを足す前の手首を追い、腕だけが上がって物体が机に残る。しかもハンドトラッキングが無い環境では HandRootDriver が書き込まないため 1 フレーム遅れで追従してしまい、症状が出ない。実機に入って初めて気づく類の壊れ方である。

発火と解放の判定

発火 — 対象の行動が連続 consecutiveHits 回届いたら、その場で開始する。単発で発火させないのは、デコーダの出力が 1 通だけ跳ねるのが普通にあるためである。N を上げるほど誤発火は減り、そのぶん発火が遅れる。

解放 — 対象でない行動が連続 consecutiveHits 回届き、かつ holdSeconds（最小保持）を過ぎたら離す。最小保持を置くのは、パケットを 1 通取りこぼしただけで動作が点滅しないようにするためである。

この規則ひとつで「想起している間は握り続ける」（HandExperiment）と「持ち上げている間ずっと保つ」（PseudoHapticsExperiment）の両方が成立する。

注意

B キーで BciDriven モードに入らない限り、UDP は手へ届かない。Tracking モードでは信号源が読まれないうえ、HandGraspAnimator も開いた姿勢を捕捉する前は書き込みを行わない。二重に止まっている。

ただし ExperimentRunner が Task セッションを開始するときは自動的に BciDriven へ切り替える。実験者がキーを押し忘れたまま試行が流れる事故はこれで塞いである。

「凍結」の仕組み

BCI 駆動へ入ると手首のドライバを enabled = false にする。ドライバは LateUpdate でしか書き込まないため、無効化されたドライバは全ボーンを最後に書いた位置にそのまま残す。姿勢をキャッシュして書き戻す方式と違い、凍結した姿勢とライブの姿勢が 1 フレームずれる余地がない。

凍結するかどうかは HandControlModeSwitch.freezeRootWhileBciDriven が決める。HandExperiment は true（指だけを見る）、PseudoHapticsExperiment は false（手首は動かして持ち上げる）。これは実験条件ではなくシーンの設計そのものなので、Settings asset ではなくコンポーネント側に置いてある。同じ場所にある grabOnBciDriven（BCI モード入りで掴みを固定するか）も同じ理由である。

SECTION 3

UDP パケットの仕様

1 パケットに 1 個の JSON オブジェクトを UTF-8 で載せる。受信は 5001 番、送信は 5000 番で、向きによってキー名が違う。どちらも python-bci-platform の実装に合わせてある。

受信（python → Unity、ポート 5001）

python-bci-platform の UdpSender が推論のたびに 1 通送る形そのままである。

{ "format_version": 1, "name": "Grasp", "class": 2, "confidence": 0.87,
  "probabilities": { "Rest": 0.13, "Grasp": 0.87 } }
キー扱い
format_version必須。1 以外は丸ごと捨てる。送信仕様が変わったことに気づけるようにするため
class判定の主役。クラス対応表（classMap）と突き合わせて行動を決める。0 は「キーが無かった」と区別できないため 1 始まり。-1 は platform の「分類なしセンチネル」なので捨てる
confidenceconfidenceThreshold 未満なら「意図なし」として扱う。捨てずに解放の連続判定へ流す
name判定には使わない。Inspector とログの可読性のためだけに読む。一致を要求すると、python 側でクラス名を変えただけで実験が止まる
probabilities読まない。キーがクラス名で動的に変わるため JsonUtility で表現できず、判定にも不要。あっても解析は通る
確信度が低いパケットを捨てないのはなぜか

確信度が足りないパケットは「意図なし」であって「無かったこと」ではない。捨ててしまうと解放の連続判定が進まず、確信度が落ちただけで握りが解けなくなる。だから None として数え続ける。

送信（Unity → python、ポート 5000）

platform 側が読むのは type / event_id の 2 つだけである。打刻はすべて同じ内容で送る。

{ "type": "grasp", "event_id": 1 }
突合は ID ではなく順序で行う

event_id が固定値なので、試行 CSV の trial_index と EEG アノテーションを ID で対応づけることはできない。「N 番目の grasp アノテーション ↔ N 番目の試行」という順序照合になる。

したがって打刻が 1 通落ちると、以降の全試行がずれる。Unity は送信の成否を試行 CSV の cue_sent 列に残すので、0 の行は必ず解析から落とすこと。失敗はその場で HMD 内とコンソールにも警告が出る。

送受信でキー名が非対称である

受信は format_version / name / class / confidence / probabilities、送信は type / event_id の 2 つだけ。連携実装で最も踏みやすい落とし穴で、受信側の形をそのまま送り返しても platform は解釈しない。

後方互換は無い

format_version が 1 でないパケットと class <= 0 のパケットは、黙って解釈されず捨てられ、UdpBciSignalSource.RejectedCount に積まれる。後方互換の分岐を置くと、送信側の設定ミスがエラーではなくデータの静かな汚染として現れる経路ができるためである。

要点

受信が途絶えると IsAvailable が false に落ち、手は最後の値で固まらず脱力する。デコーダが落ちたまま握りっぱなしになる事故を防ぐための設計である。

ただし最小保持（holdSeconds）のあいだは例外で、受信が途絶えていても動作を続ける。1 通の取りこぼしで動作が点滅しないようにするためである。判定は UdpBciSignalSource.staleAfterSeconds（既定 0.5 秒）で行う。これは実験条件ではなく通信の健全性判定なので、設定 asset ではなくコンポーネント側にある。

SECTION 4

どこに何を置くか

Settings asset に置くのは実験条件として動かす値だけである。リグの定数やキー割り当てを混ぜると、「実験中にどれを触ってよいか」が asset を見ても分からなくなる。

asset は実験ごとに 1 枚である

2 つのシーンは別の実験なので、asset を共有しない。各シーンが参照する Settings asset は 1 枚だけであり、片方を触ってももう一方には一切影響しない。

asset参照するシーン内容
HandExperimentSettingsHandExperiment のみUDP 受信 / 送信・クラス対応表・発火判定・動作のタイミング・実験設定・記録
PseudoHapticsSettingsPseudoHapticsExperiment のみ同上の共通部分 ＋ 持ち上げ・C/D 比・掴み / 解放・物体の復帰・アバター

共通する部分（UDP 受信・イベント UDP 送信・動作のタイミング）はフィールドの定義を基底クラス BciSignalSettings に 1 度だけ書いてあるが、値は asset ごとに独立に持つ。定義の重複は避けつつ、実験は分かれている。

要点

スカラーは毎フレーム読み直される前提なので、Play Mode 中に Inspector で書き換えればその場で効く。派生キャッシュを持つもの（UdpPacketReceiver のソケット、UdpEventSender の宛先）だけが Changed イベントを購読して作り直す。

実験中に触ってよい値

被験者ごとに調整してよいのは avatarHeadOffset（PseudoHapticsSettings）だけである。他は全被験者で固定する。とくに foreperiodSeconds（予告 2.0 秒）と closeSeconds / openSeconds は動かしてはならない。前者を可変にすると検出したい脳波信号が有意に減弱し、後者が変わると主観評価が被験者間で比較できなくなる。

confidenceThreshold と consecutiveHits はセッション前の調整で決め、本番のあいだは動かさない。途中で変えると、同じ被験者の試行が別の判定条件で混ざる。

補足

両 asset の既定値は EditMode テスト（Asset_*）が実物を読んで押さえている。検証でタイムラインや C/D 比や出力先を書き換えたまま戻し忘れると、テストが落ちて気づける。

使い方

SECTION 6

実験の実行

2 つのシーンは回し方が違う。HandExperiment は試行タイムラインを持ち、PseudoHapticsExperiment は持たない。

HandExperiment — 試行を回す

experimentMode を Off 以外にして Enter を押すと ExperimentRunner が試行タイムラインを駆動する。1 回の実行で回す試行数は trialCount で決める。

ランナーは動かず、試行も回らない。B キーで手動に BCI 駆動へ切り替えて手を触る、動作確認と調整のための状態である。

  • 結線の確認、机キャリブレーション、avatarHeadOffset の調整をこの状態で行う
  • デコーダの疎通確認もここでする。Space で代役入力もできる
  • Enter を押しても何も起きない。セッションを始めるには先にモードを変える

キューだけを出し、手は動かさない。分類器の学習データを取る。

  • 発火なし・主観入力なし。Unity はキューを出して打刻するだけ
  • 手の駆動モードは Tracking のままにする。手が動くと想起以外の運動が脳波に乗る
  • 陽性クラスは各試行の [-1.5, 0.0]、陰性クラスは同じ試行の安静区間から取る

BCI が発火して仮想の手が握られ、試行ごとに主観的一致度を答えてもらう。

  • セッション開始時に自動で BciDriven へ切り替わる。キーの押し忘れ事故を塞いである
  • 復帰区間のあとに机上の 7 ボタンが出る。指先で −3（早すぎ）〜 0（ちょうど）〜 +3（遅すぎ）を押す
  • 回答が滞る場合は実験者が 1〜7 キーで代打ちできる。上限時間は設けない（遅い回答を黙って捨てないため）
  • ボタンはいちど指先が離れるまで反応しない。机に指を置いたまま次の試行を迎えても、勝手に確定しない

Training と Task はタイムラインを共有し、違いは発火の有無と主観入力の有無だけである。構造を揃えるのは、トレーニングで作ったモデルの入力分布をタスクでずらさないためである。

1 試行の構造

安静 3.0 s（±0.5 s ジッタ）  →  予告 2.0 s（3-2-1 カウントダウン、固定）  →  t=0 キュー
   →  想起の保持 3.0 s  →  復帰 2.0 s  →  ［Task のみ］主観入力
2 つのジッタの役割は正反対である

安静区間にジッタを入れるのは、試行の開始時刻が完全に周期的だと、脳波を一切見ない周期発火ベースラインと区別がつかなくなるからである。

予告から t=0 までを固定するのは、この間隔が可変だと運動前活動が有意に減弱するからである（Cui & MacKinnon 2009, P < 0.005）。この 2 つは両立する。

PseudoHapticsExperiment — 持ち上げを回す

試行タイムラインは持たない。B で BCI 駆動へ入り、そこから持ち上げの想起を繰り返す。

  1. D で机を実際の机に合わせ、C で手首を較正する
  2. B を押す。手が閉じて TargetCube を掴んだ状態になる（grabOnBciDriven）。ここで把持は成立済みであり、以降デコードが揺れても取り落とさない
  3. 持ち上げの想起（または ↑）で腕が上がる。上がり方は liftDriveMode で決まる。持ち上げが効くのは BCI 駆動のあいだだけである（トラッキングのままで腕が上がると、被験者が自分で動かしたのか BCI が動かしたのか分からなくなる）
  4. 指令変位に cdRatio を掛けたものが実際の腕の動きになる。LiftTask が到達高さを計測する

持ち上げの 2 つのモード

OneShot — 発火を引き金に、台本どおり liftHeight まで上がり、holdSeconds 保ち、liftReturnSeconds で戻る。到達高さと所要時間が全試行で揃うので、C/D 比を振ったときの重さ知覚の比較が成立する。既定はこちら。

Continuous — 信号が続く間だけ liftSpeed で上がり続け、liftHeight で頭打ちになる。途絶えたら戻る。被験者の制御感は高いが、試行ごとの到達高さが揃わない。

C/D 比の掛け方は「普通に腕を動かしたとき」と同じである

BciLiftDriver は指令変位を CdRatioMath.Scale に通す。実トラッキング変位を扱う CdRatioHandProcessor と同じ関数なので、効き方が一致する。変位の出どころが違うので二重には掛からない。

BciLiftDriver は Transform を直接書くため、HMD もハンドトラッキングも無い環境で動く。CdRatioHandProcessor は hand.isTracked でなければ何もしないので、実機なしの確認はこちらの経路で行う。

キー操作

実験中のキーは [Systems]/Hotkeys が一手に引き受ける。割り当ては ExperimentHotkeys の Inspector で変えられる。把握と持ち上げの代役入力だけは KeyboardBciSignalSource にある（信号ソースの一部であって操作系ではないため）。

キー動作シーン
Bトラッキングと BCI 駆動の切り替え。Pseudo では同時に物体を掴む両方
C手首の回転オフセットの再測定（手を平らにして脱力してから押す）両方
D仮想の机を実際の机に合わせるキャリブレーションの開始両方
Enter / Esc実験セッションの開始 / 中断Hand
1〜7主観的一致度 −3〜+3 の代打ちHand
Space把握の代役入力両方
↑持ち上げの代役入力。BCI 駆動のあいだだけ効くPseudo
BCI 入力とキー入力は併用できる

CompositeBciSignalSource が UDP のソースとキーボードのスタブを最大値で束ねる。デコーダを繋いだまま、いつでもキーで手動介入できる。片方だけを繋いだ構成でも同じように動く。

試行 CSV の 8 列

各列が特定の指標に 1 対 1 で対応し、どれも他の列や設定から導出できないものだけに絞ってある。

列その列が支える指標
trial_index試行の通し番号。EEG との突合はこの順序で行う

cue_sent0 なら打刻が届いておらず、その試行の EEG は解析から落ちる
fire_unixΔt の本体と検出率。空欄が未発火の試行

主要な導出値

Δt ＝ fire_unix − cue_unix。主要評価項目である。

試行成功率 ＝ |Δt| ≤ 200 ms かつ fire_count == 1 の試行の割合。

列に持たない値

block_index はブロックの概念ごと無くなった。1 回の実行は試行の列 1 本である。applied_unix は発火の予約（delay_ms）が無くなり fire_unix と常に同値になったため落とした。delta_ms は引けば出る。peak_grasp_level は把持レベルが 0/1 を速度制限したものである以上ほぼ常に 1 になる。grasp_level_series は closeSeconds と fire_unix から再構成できる。いずれも冗長なので持たない。設定値も行ごとには出さず、隣のスナップショットに 1 回だけ書く。

注意

打刻に失敗した試行は、その EEG が解析から落ちるだけでなく、以降の突合を全部ずらす。打刻はすべて同じ内容（event_id: 1）で送るため、突合は順序で行うしかない。1 通の欠落が以降の全対応をずらす。送信失敗はその場で HMD 内とコンソールに警告が出るので、実験者が必ず確認し、cue_sent が 0 の行は解析から落とすこと。

セッション前に決めること

発火の判定が Unity 側へ移ったので、セッション前に決めるのは閾値と連続回数の 2 つである。トレーニング計測で作ったモデルを使い、Off モードで実際にパケットを流しながら詰める。

値上げると下げると
confidenceThreshold誤発火が減り、検出率も下がる検出率が上がり、誤発火も増える
consecutiveHits誤発火が減り、発火が遅れる反応が早くなり、単発の跳ねで発火する

consecutiveHits の 1 回ぶんの遅れは、python 側の interval（推論間隔）で決まる。既定の 5 Hz なら 1 回あたり 0.2 秒であり、N=3 は約 0.4 秒の遅れを意味する。Δt の許容が ±100 ms であることを考えると、N を上げるほどタイミング精度は取り返せなくなる。誤発火とのトレードオフをここで決める。

実験中は動かさない

閾値と連続回数はセッション前に決め、本番のあいだは固定する。途中で変えると、同じ被験者の試行が別の判定条件で混ざり、Δt の分布が何を測ったものか分からなくなる。

テスト

EditMode テストは Unity Test Runner（Window > General > Test Runner）から実行する。対象アセンブリは PseudoHaptics.Tests.EditMode。

テストの対象は、ソケットも Unity のランタイムも要らない純粋な static クラスに切り出してある（BciPacketDecoder / BciClassMap / ConsecutiveHitCounter / BciHoldSchedule / LiftTrajectory / TrialSchedule / TrialCsvWriter / EventPacketEncoder / PressTrigger / GraspLevelSmoother / GraspTrigger / CdRatioMath）。加えて Asset_* テストが両方の Settings asset の実物を読み、既定値がプロトコルどおりであることを押さえている。

SECTION 9

まとめ・Q&A

  • Unity の役割はキュー提示・発火の判定と描画・記録の 3 つ。脳波の計測とデコードは python-bci-platform が持つ
  • 発火の判定は Unity 側にある。閾値と連続 N 回は設定 asset にあり、実験者がその場で振れる
  • UDP は受信 5001 / 送信 5000 で、向きによってキー名が違う。受信は format_version: 1 が必須で、旧版と class <= 0 は捨てる
  • 2 つのシーンは別の実験。Hand は把握を、Pseudo は腕の持ち上げを想起させる。参照する asset は 1 枚ずつに分かれている
  • 実験モードは Off（自由制御）/ Training / Task の 3 つ。Training と Task の違いは発火の有無と主観入力の有無だけ
  • 試行 CSV は 8 列。設定値は隣のスナップショットに 1 回だけ書く
  • 打刻は event_id: 1 固定なので、EEG との突合は順序で行う。cue_sent が 0 の行は必ず落とす
  • 実験中に被験者ごとへ変えてよいのは avatarHeadOffset だけ
手が動きません。何を確認すればよいですか

上から順に確認します。

  • モード。B キーで BciDriven に入っていますか。Tracking のままだと二重に止まっています（Task セッションを開始すれば自動で切り替わります）
  • パケット形式。UdpBciSignalSource.RejectedCount が増えていれば、送信側の format_version が 1 でないか、class が 0 以下です
  • ポート。UdpPacketReceiver.BoundPort が -1 なら別プロセスが 5001 を掴んでいます
  • クラス対応表。届いている class が classMap に登録され、目的の action が割り当たっていますか。LatestClass と LatestAction で確かめられます
  • 確信度と連続回数。confidenceThreshold を超えるパケットが consecutiveHits 回続いていますか。閾値を 0、回数を 1 にすれば切り分けられます

logPackets をオンにすると、受け入れたパケットが行動の判定結果つきで毎回コンソールに出ます。

PseudoHapticsExperiment で B キーを押すと何が起きますか

手が閉じて TargetCube を掴んだ状態になります（HandControlModeSwitch.grabOnBciDriven）。腕はまだ上がりません。上がるのは、そのあと持ち上げの想起（または ↑）が届いてからです。

このシーンでは把握は検証対象ではなく前提条件です。把握のデコードが揺れて物体を取り落とすと、検証したい持ち上げのほうが成立しなくなるため、モード入りで掴みを固定しています。grabLevelThreshold / releaseLevelThreshold は自由制御モード（Off）で手動に掴むときにだけ効きます。

なお HandExperiment では grabOnBciDriven は false です。あちらは把握そのものを測るので、掴みを固定してしまっては意味がありません。

持ち上げていないのに腕が動きます。原因は何ですか

BciLiftDriver 以外に、手首を動かす経路が 4 つあります。CommandedHeight が 0 のままなら持ち上げ以外が原因です。

  • C キーの手首較正。HandRootDriver.Calibrate() はトラッキングされた手首を referenceEuler へ写す offset を測り直します。押した瞬間に手首の向きが一段跳び、IK の前腕と肘が追従します
  • トラッキングのロスト。HandRootDriver は hand.isTracked でなければ書き込まないため、手首は最後の位置に取り残されます。一方 FirstPersonAvatarAnchor は毎フレーム胴をカメラへ寄せ続けるので、腕が伸びるように見えます
  • 机のクリアランス。ClampAboveSurface が手首を机の上端 + clampClearance より下へ行かせません。手を机へ押し付けると腕が持ち上がります
  • C/D 比。cdRatio が 1 でなければ、持ち上げの指令に対して腕が違う量だけ動きます
「平滑化」という処理は何ですか。必要ですか

信号のノイズ除去ではありません。GraspLevelSmoother は把持レベルを 0 から 1 へ closeSeconds かけて線形に動かすだけの開閉アニメーションの速度制限です。呼び名が誤解を招くので、資料では「開閉の速度制限」と書いています。

必要です。これが無いと手は 1 フレームで握り込み、grasp_reach_unix（把持到達時刻）も測れません。また 0/1 の硬い分類を出すデコーダと連続的な確信度を出すデコーダのどちらを繋いでも、手の見た目の動きが同じになります。

なぜ設定 asset を 2 つに分けているのですか

別の実験だからです。HandExperiment は把握を想起させて発火のタイミング精度を測り、PseudoHapticsExperiment は腕の持ち上げを想起させて C/D 比による重さ知覚を測ります。1 枚に混ぜると、いま自分がどちらの条件を触っているのかが分からなくなります。

各シーンが参照する asset は 1 枚だけです。共通する部分（UDP・発火判定・動作のタイミング）はフィールドの定義を基底クラス BciSignalSettings に 1 度だけ書いてありますが、値は asset ごとに独立に持ちます。片方を触ってももう一方には影響しません。

なぜ発火判定を python 側ではなく Unity 側に置いたのですか

閾値と連続回数を実験者がその場で振れるようにするためです。python 側に置くと、被験者ごとの調整のたびに実験を止めて別リポジトリの設定を触ることになります。

加えて、python-bci-platform の送信仕様には発火を表すキーがありません。送るのは format_version / name / class / confidence / probabilities の 5 つだけで、「いつ動かすか」を表現する余地がない。判定を Unity 側へ置くと、platform を改造せずに繋がります。

引き換えに、delay_ms による遅延補償は無くなりました。発火は連続 N 回が成立したフレームで即座に起きます。

HMD の中の文字が四角（豆腐）になります

TextMeshPro の既定フォント LiberationSans SDF は ASCII しか持たないためです。表示文字列は CueDisplay の Inspector に出してあり、既定値は必ず描ける ASCII（GO / RATE / END など）にしてあります。日本語で出したい場合は、日本語グリフを含む TMP フォントアセットを用意してテキストに割り当ててください。カウントダウンの数字は言語に依存しません。

Δt が 0 に集まれば「イメージと一致した」と言えますか

言えません。Δt は「キューからの発火誤差」であって「イメージ開始からのズレ」ではなく、被験者が教示どおり t=0 に想起を始めたという仮定に依存しています。キュー基準での被験者側のばらつきは 100 ms 台に達します（Jochumsen et al. 2019 の報告値は 11.73 ± 165 ms。桁の目安）。

だから主観的一致度を対で取ります。Δt と主観の対応こそが本研究の新規性の核です。

発火しない試行が多いのですが、実験として成立しますか

成立します。想像課題の TPR は文献値で 65〜75% であり、3 割前後の試行が発火しない前提で設計してあります。検出率と Δt は別々に報告する指標で、発火しなかった試行は検出率の分母に入り、発火した試行だけが Δt の分布を作ります。

検出率が極端に低い場合は confidenceThreshold と consecutiveHits を下げて調整できますが、そのぶん誤発火（rest_fire_count）が増えます。両方を報告してください。
