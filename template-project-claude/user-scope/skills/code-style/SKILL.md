# コーディングスタイル (code-style)

このスキルはコードの新規記述・リファクタリング・レビュー時の **命名規則・コメントの付け方の強制適用ルール** を提供する。全プロジェクト共通の土台であり、プロジェクト固有の上書きは各プロジェクトの `CLAUDE.md` が持つ。

## いつ発火させるか

- 新規にコードを書く（言語不問）
- 既存コードをリファクタリングする
- コードレビュー・自己チェックを行う
- 命名やコメントの付け方について質問された
- コアドキュメント（`CLAUDE.md` / `README.md` / メモリファイル）や自作 skill/agent の Markdown を新規作成・編集する

## プロジェクト固有ルールとの関係

本スキルは言語横断の一般原則だけを持つ。コメントを書く言語、ログの扱い、絵文字の可否といった **プロジェクトごとに割れる方針は各プロジェクトの `CLAUDE.md` に従う**。両者が衝突した場合は `CLAUDE.md` が優先する。

正典となる詳細版をリポジトリに置いているプロジェクトでは（例: `docs/CODING_STYLE_GUIDE.md`）、そちらの各論を優先して参照する。

## 適用範囲

本スキルの命名・コメント原則は **ソースコードに限らず** Markdown にも適用する。「なぜコメントを書くか」「冗長な説明を避けるか」の原則がドキュメント本文にもそのまま当てはまるためである。

- コアドキュメント: `CLAUDE.md` / `README.md` / メモリファイル
- 自作した skill / agent の `SKILL.md` および agent 定義 Markdown

対象外: 外部リポジトリから取り込んだ vendored skill と、`_archived/` 配下。上流との差分を避けるため書き換えない。

## 基本理念

1. **一貫性 > 正しさ** — 既存コードベースに規約があるなら、たとえ自分の好みと違ってもそれに従う。
2. **名前で語らせ、コメントで補う** — 良い名前はコメントの必要を減らす。まず名前を磨き、それでも伝わらない「なぜ」をコメントにする。
3. **コメントは資産であり負債** — 保守コストを伴う。書くほど良いのではなく、コードで表現できないものだけに絞る。

## 命名の普遍原則

- **意図が読み取れる名前にする**（`d = 30` ではなく `expiration_days = 30`）。
- **検索可能な名前にする**。マジックナンバー・1 文字変数は避け、定数に名前を付ける。
- **スコープの長さと名前の長さを比例させる**。ループカウンタの `i` は数行で閉じるなら許容。
- **型・単位・意味を名前に埋め込む**（`timeout_ms`、`max_retry_count`、`is_active`、`user_list`）。
- **否定形の名前を避ける**（`is_not_valid` ではなく `is_valid`）。
- **対称的な語彙を統一する**（`get/set`、`open/close`、`begin/end`、`create/destroy`）。同じ概念に `fetch` `get` `retrieve` を混在させない。**1 概念 1 語**。
- **略語を乱用しない**。広く通じるもの（`id` `url` `db` `max`）以外は省略しない。

## コメントの普遍原則

最重要原則: **「何を(what)」ではなく「なぜ(why)」を書く。** コードは what を既に表している。

**価値の高いコメントの類型**

| 類型 | 内容 |
|------|------|
| 意図 | なぜこの実装を選んだか |
| 警告 | 変更時の危険・制約 |
| 外部参照 | 仕様・チケット・バグへのリンク |
| 非自明な根拠 | 定数や式の由来 |
| TODO/FIXME | 未完成・既知の問題（担当者・文脈付き） |

**避けるべきコメント**

- コードの言い換え（当たり前の説明）
- コメントアウトされた古いコード → バージョン管理があるので削除する
- **嘘をつくコメント** — コードを変えたらコメントも必ず更新する。古いコメントは無いより有害
- 履歴コメント（`# 2024-01 田中 修正`）→ Git blame に任せる

## 出力とドキュメントの冗長性

- **冗長なデバッグログを避ける。** `print` / `console.log` / `System.out.println` / `Debug.Log` などの一時トレース出力を本番コードに残さない。恒常的に必要なログはログレベル（debug/info/warning/error）を使い分けて最小限にする。一時デバッグ出力はコミット前に削除する。
- **冗長な説明を避ける。** コメント・docstring・ドキュメント本文とも、同じ内容を複数箇所で言い換えて繰り返さない。1 つの事実は 1 箇所にだけ書き、他はそこへの参照に留める。既にコードや見出しが表している情報を文章でなぞり直さない。1 文で言えることを 3 文に引き伸ばさない。

## 言語別命名規則（要約）

| 言語 | 変数・関数 | クラス・型 | 定数 |
|------|-----------|-----------|------|
| Python | `snake_case` | `PascalCase` | `UPPER_SNAKE_CASE` |
| JavaScript / TypeScript | `camelCase` | `PascalCase` | `UPPER_SNAKE_CASE`（真の不変値のみ） |
| Java | `camelCase` | `PascalCase` | `UPPER_SNAKE_CASE` |
| C# | メソッド`PascalCase` / ローカル`camelCase` | `PascalCase` | `PascalCase`（`const`/`static readonly`） |

真偽値は言語を問わず `is` / `has` / `can`（TS/JS は `should` も可）で始める。

## ケース表記チートシート

| 表記名 | 形 | 主な用途 |
|--------|-----|----------|
| `snake_case` | `user_count` | Python 変数/関数、DB カラム |
| `UPPER_SNAKE_CASE` | `MAX_RETRIES` | 定数（全言語共通） |
| `camelCase` | `userCount` | JS/TS/Java の変数・メソッド |
| `PascalCase` | `UserCount` | クラス・型（全言語共通）、C# メソッド |
| `kebab-case` | `user-count` | ファイル名、URL、CSS クラス |

## クイックチェックリスト

### 命名

- [ ] 名前だけで意図が読み取れるか（`d` `tmp` `data2` が残っていないか）
- [ ] 言語の標準ケース表記に従っているか
- [ ] boolean は `is`/`has`/`can` で始まっているか
- [ ] マジックナンバーが名前付き定数になっているか
- [ ] 同じ概念に複数の語（get/fetch/retrieve）が混在していないか
- [ ] 略語を乱用していないか

### コメント

- [ ] 「なぜ」を説明しているか（「何を」の繰り返しになっていないか）
- [ ] コードと矛盾する古いコメントが残っていないか
- [ ] コメントアウトされた死んだコードを削除したか
- [ ] 公開 API にドキュメントコメント（docstring/JSDoc/Javadoc/XML）があるか
- [ ] TODO/FIXME に担当者・文脈が付いているか
- [ ] 名前を改善すれば消せるコメントではないか

### 出力・冗長性

- [ ] 一時デバッグ出力（print/console.log 等）が残っていないか
- [ ] 恒常ログはログレベルで整理されているか
- [ ] 同じ説明を複数箇所で言い換えて繰り返していないか

### プロジェクト規約

- [ ] `CLAUDE.md` のコメント言語・表記ルール（絵文字の可否など）に従っているか
- [ ] コアドキュメント・自作 skill/agent の Markdown にも命名・コメント原則を適用したか
