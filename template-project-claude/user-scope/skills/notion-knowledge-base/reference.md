# Notion 知識ベース + ローカルミラー

Notion を長期知識ベースとして使い、その内容をローカルの Markdown ミラーへ一方向で pull する仕組みの設計とセットアップ手順。出典は記事「毎回初対面のAIを参謀に変える3層記憶スタック」（Obsidian 版）で、本プロジェクトでは Obsidian を Notion に置き換えたうえで、Obsidian が持っていた「ローカルファイルである」利点をミラーで補っている。

## アーキテクチャ

```
Notion（人間が書く・探す・読む・見た目）
  │  notion_sync.py が REST API で pull（一方向・増分）
  ▼
~/.notion-mirror/（全プロジェクト共通。同期が書く領域は派生物・手編集禁止）
  │  Claude Code が Grep / Read で走査（低コスト）
  ▼
整理・要約・照合
  │  Notion MCP（mcp__notion__create-a-page 等）で書き戻し
  ▼
Notion  →  次の pull でミラーへ反映
```

得意な側に役割を寄せている。Notion は検索性・可読性・見た目に優れ、ローカルファイルはエージェントの走査コストが小さい。

## 設計判断とその理由

### なぜローカルミラーを置くか

記事の中核は「コーパス全体を一度にコンテキストへ載せて判断する」ことにある。これは Obsidian がローカル Markdown だから成立する。Notion は MCP 経由の API 読み取りとなり、ページごとにツール呼び出し・ページネーション・トークン課金が発生するため、ワークスペース全体の投入が成立しない。

ミラーを置くと、読み取りが `Grep` / `Read` になり、絞り込んでから必要な箇所だけ読めるため全件走査が現実的なコストに収まる。記事の中核メカニズムが Notion 構成でも復活する。

### なぜ一方向に限定するか

双方向同期には ID マッピング、競合解決、Notion ブロックと Markdown の非可逆変換（トグル・コールアウト・DB・relation・コメント）、リネームと削除の検出が必要で、実装量とデータ損失リスクが跳ね上がる。

**同期が書いた領域を「いつでも取り直せる派生物」と定義し、手で編集しない**という約束を置けば、競合は構造的に発生しない。AI の生成物は Notion へ書き、次の pull でミラーへ降りてくるため、書き手は常に 1 方向に保たれる。

この約束が及ぶのは同期が書いた領域だけである。`_` で始まる直下のディレクトリ（`_md/` の原文・`_html/` の清書版）は同期の管理外で、手で編集してよく、取り直しの対象にもならない（「解説資料の置き場所」参照）。

### なぜ MCP ではなく REST API で pull するか

MCP 経由で pull すると、全ページの本文がモデルのコンテキストを通過する。ミラー化の目的である読み取りコストの削減を、取り込み処理そのものが打ち消してしまう。REST API を直接叩くスクリプトなら本文はコンテキストを一切通らず、処理も速く、将来的な自動実行にも乗せられる。

### なぜ記録層と知識層を分けるか

作業ログだけを溜めると、「この論点について何を知っているか」を引いたときに日付つきの日記が返る。答えを得るには当時の文脈ごと読み直すしかなく、蓄積が増えるほど読み直しの量も増える。

Zettelkasten の permanent note、Matuschak の evergreen note、PARA の Resources はいずれも同じ処方を出している。日付に紐づく記録と、概念に紐づく主張を別物として扱い、後者は概念単位・書き換え前提にする。知識層のタイトルを完全な主張にするのは Matuschak の「タイトルは API」で、タイトルだけで他のノートから参照できる状態を作るためである。

分離の実務上の効果は、**知識層だけを走査対象にできる**ことにある。`層: 知識` で絞れば、記録層 100 件を読まずに主張だけを一望できる。

### なぜトピックを relation にしないか

語彙の統制だけを見れば、トピック_DB を作って relation で参照するほうが強い。Notion 側で入力が既存語に強制され、リネームが伝播し、backlink も得られる。

採用しなかったのは**ミラーの読み取りが壊れる**ためである。`notion_sync.py` は relation をページ ID の配列として frontmatter に書く（`property_to_value()`）。トピックを relation にすると `Keywords: [bci, eeg]` が `Keywords: [3afb6e7e-…, 39cb…]` になり、`Grep "^Keywords: .*bci"` が効かなくなる。読み取りを安価な grep に寄せるという設計の中心が崩れる。

そこで **multi_select のまま、語彙の文字列を DB 間で揃える**方針を取った。統制は Notion の機能ではなく規約（正規化規則 + コア語彙 + 新語の承認制）で行う。relation は DB 間の 3 本だけに限定している。

### なぜ種別を select にするか

`KeyWords` に種別とトピックを同居させていた頃、「種別を必ず 1 つ含める」はプロンプトでしか強制できず、選択肢一覧も 2 軸が混ざって候補が濁っていた。

`種別` を独立した select にすると、Notion のビューで直接グループ化・フィルタでき、選択肢一覧が 10 語で閉じる。さらに `notion_sync.py` の `page_kind()` が `種別` / `Type` の select を読んでミラーをサブディレクトリへ分割する仕組みを既に持っていたため、**スクリプトを 1 行も変えずに** `研究ノート_DB/知見/` のような構造と `Grep "^種別: 課題"` が手に入った。

### なぜ全プロジェクト共通の 1 箇所に置くか

知識コーパスはリポジトリ単位ではなく 1 つである。派生プロジェクトすべてが同じミラーを参照することで、記事の言う蓄積効果がリポジトリをまたいで効く（Vault 単位で閉じる記事の構成より広い）。

## セットアップ

同期スクリプトと Notion MCP が **同じ `NOTION_TOKEN` を共有する**。認証はこの 1 本だけ。

### 1. Notion インテグレーションを作成する

1. <https://www.notion.so/my-integrations> を開き、内部インテグレーションを作成する
2. 権限は**読み取りに加えて、コンテンツの挿入・更新も有効にする**（MCP 側が同じトークンで書き込むため）
3. 発行されたトークン（`ntn_` で始まる文字列）を控える

### 2. ページをインテグレーションに共有する

対象のページまたはデータベースを Notion で開き、右上のメニューから作成したインテグレーションに接続する。**共有されたものだけが同期・書き込みの対象**になるため、共有範囲がそのまま操作範囲の制御になる。

### 3. トークンを設定する

次の順で探索される。後ろほど優先度が低い。

| 場所 | 用途 |
|---|---|
| 環境変数 `NOTION_TOKEN` | シェルで export。**MCP サーバはここからしか読めない** |
| `<プロジェクト>/.env` | そのプロジェクト専用のトークンを使いたいとき |
| `~/.claude/.env` | 全プロジェクト共通（同期スクリプト用の既定） |

```
NOTION_TOKEN=ntn_xxxxxxxxxxxxxxxxxxxx
NOTION_MIRROR_DIR=~/knowledge/notion-mirror   # 任意。既定は ~/.notion-mirror/
```

**MCP サーバは環境変数しか見ない。** `~/.claude.json` の登録は `${NOTION_TOKEN}` のリテラル参照になっており、Claude Code 起動時の環境から展開される。`~/.claude/.env` に書いただけでは MCP には渡らないため、シェルの設定（`.zshrc` 等）で export しておくこと。同期スクリプトは `.env` も読むので、そちらは export なしでも動く。

### 4. MCP サーバの登録

```bash
claude mcp add --scope user notion --env 'NOTION_TOKEN=${NOTION_TOKEN}' -- npx -y @notionhq/notion-mcp-server
```

シングルクォートで囲み、`${NOTION_TOKEN}` が**展開されずリテラルのまま**保存されることを確認する（`~/.claude.json` に実トークンが書かれていたら書き直す）。登録後は Claude Code の再起動が必要。

### 5. 初回同期

```bash
python3 ~/.claude/scripts/notion_sync.py --dry-run   # 取得対象を確認
python3 ~/.claude/scripts/notion_sync.py             # 実行
```

以降は `/notion-sync` で更新する。2 回目以降は更新されたページだけを取得する。

## Notion 側の構成

書き込み先は **Research Management ページ内の Research Note**。

```
Research Management
├─ 今月の目標 / クイックメニュー
├─ MTG            → ミーティング議事録_DB
├─ Research Note  → 研究ノート_DB      ← /notion-digest の追記先
└─ Academic ...   → 学会管理_DB
```

このほか `Reference List`（論文ノート、100 件超）が共有されており、ミラーには `Reference-List/` として入る。

### 研究ノート_DB

database ID: `30cb6e7e-18a2-81ef-814e-eabea30a4da1`
data source ID: `30cb6e7e-18a2-8144-b858-000b9f180525`

| プロパティ | 型 | 用途 |
|---|---|---|
| `Title` | title | 記録層 / 課題層は名詞句（20 字以内）。知識層は完全な主張（30 字以内）。日付は入れない |
| `概要` | rich_text | 1〜2 文の要約。一覧ビューで中身が見えるようにする |
| `Date` | date | 記録層は対象日（週次は週の最終日）、知識層は初版作成日 |
| `種別` | select | 下記 10 語。ミラーのサブディレクトリ名になる |
| `Keywords` | multi_select | トピック語のみ 2〜5 個。種別語は入れない |
| `関連文献` | relation → Reference List | 依拠した / その回に調べた論文（双方向。相手側は `引用ノート`） |
| `関連ノート` | relation → 研究ノート_DB | **単方向**。記録の連鎖と知識層への切り出しリンク |
| `関連MTG` | relation → ミーティング議事録_DB | 出所の議事録（双方向） |

`関連ノート` は単方向なので、**リンクを張ったら相手側にも書き返す**。Notion の dual_property が自動でやっていたことを明示的に行う。書き戻すときは必ず現在値を読んでから追加する（上書きすると既存のリンクが消える）。

### 削除したプロパティ

| プロパティ | 削除の理由 |
|---|---|
| `層`（formula） | `種別` から一意に決まる派生値だった。ミラーは `研究ノート_DB/<種別>/` に分かれており `Grep "^種別: 知見"` で足りる。`notion_sync.py` がディレクトリ分割に使うのは `種別`（`KIND_PROPERTY_NAMES`）であって `層` ではないため、消しても検索性は落ちない |
| `状態`（select） | `課題` 専用だったが、`課題` は無人記録では起票せず手動のみで実績ゼロだった。課題の運用を始める時点で戻せばよい |
| `被参照ノート`（relation） | `関連ノート` の dual 同期側。列が 2 つに割れて読みにくく、単方向 + 明示的な書き返しで同じ結果が得られる |

### アイコン

作成時に必ず明示する。Notion がこの DB の既定を暗黙に適用する挙動は文書化されておらず、依存しない。書式は `{"type": "icon", "icon": {"name": ..., "color": ...}}` で、`mcp__notion__API-post-page` の引数として properties と並べて渡す。

| 種別 | name / color |
|---|---|
| `進捗` `開発` `実験` `議論` `日常` `メモ` | `document` / gray |
| `知見` | `light-bulb` / yellow |
| `文献` | `book` / brown |
| `アイデア` | `stars` / orange |
| `課題` | `warning` / red |

名前は実在するものに限られる。`bulb` は 400 で弾かれ、`sparkle` は `stars` へ正規化された。新しい名前を使うときは既存ページへの `patch-page` で先に確かめること。

### 種別の語彙（10 語）

`進捗` / `開発` / `実験` / `議論` / `日常` / `メモ`（記録層）、`知見` / `文献` / `アイデア`（知識層）、`課題`（課題層）。

**種別は勝手に増やさない。** トピック語の追加はユーザーの承認を得る。付け方の手順は `SKILL.md` の「Keywords の付け方」を参照。

### Reference List DB

database ID: `36cb6e7e-18a2-801c-bb19-dce294fcd4d8`
data source ID: `97cb6e7e-18a2-8315-bff9-07a71c43a2ba`

このデータベースは**複数のデータソース**を持つ（実体は上記 1 つと、`Name` しか持たない空の `f69b6e7e-18a2-8266-af2e-072b218064ef`）。そのため API バージョン 2022-06-28 の `/databases/{id}` が 400 を返す。同期スクリプトは 2025-09-03 で取り直すフォールバックを持っており、ディレクトリ名は正しく解決される。

`Keywords` は研究ノート_DB と**同じ語彙**を共有する。正規化規則（小文字・ハイフン区切り・英語）に揃えてあり、コア語彙は 3 回以上出現する約 37 語。

## ミラーのレイアウト

```
~/.notion-mirror/
  _manifest.json                                   # page_id -> path / last_edited_time
  _md/python-bci-platform/docs/ROADMAP.md          # 解説資料の原文（同期の管理外）
  _html/研究ノート_DB/知見/ROADMAP.html             # その清書版（同期の管理外）
  研究ノート_DB/開発/2026-08-01-被験者間転移学習の-analysis-モード統合-3afb6e7e.md
  研究ノート_DB/知見/2026-08-01-被験者間-EEG-分類では古典パイプラインが-3afb6e7e.md
  Reference-List/2026-07-31-Brain-Computer-Interfaces-3aeb6e7e.md
  ミーティング議事録_DB/...
  学会管理_DB/...
  pages/2026-02-19-Research-Management-30cb6e7e.md   # DB 外のページ
```

- ディレクトリはデータベース名から決まる。`種別` / `Type` の select があればその下にさらに分かれる（`page_kind()`）。データベース外のページは `pages/` に入る
- ファイル名末尾の短縮 ID により、Notion 側でタイトルを変えてもパスが安定する
- frontmatter に Notion のプロパティがそのまま入るため、`Grep "^種別: 課題"` や `Grep "^Keywords: .*bci"` のような絞り込みが本文検索と同じコストで行える
- relation は**ページ ID の配列**になる。ID からファイルへは `_manifest.json` で解決する

### 変換の方針

未対応のブロック種別は `<!-- 未対応ブロック: <type> -->` として残す。内容を黙って落とさないことを優先している。段組み（`column_list` / `column`）と同期ブロックは中身をそのまま展開する。見出しは `heading_1` から `heading_6` まで対応する（Notion の実データには API 仕様にない `heading_4` が現れる）。

`unsupported` は Notion API 自身が本文を返さないブロック種別で、こちらでは対処できない。

## 記事から採用しなかったもの

| 記事の要素 | 判断 | 理由 |
|---|---|---|
| 双方向同期 | 採用しない | 競合解決とブロック変換の非可逆性でリスクが実装量に見合わない |
| 孤立ノート検出（週次lint） | **採用** | relation を入れたことで実現可能になった。専用の実装は要らず、ミラーへの grep で足りる（`SKILL.md` の「健全性チェック」） |
| フォワードリファレンス（未作成ノートへの仮リンク） | 採用しない | Notion に未解決リンクの概念がない |
| 日次 / 週次の自動スケジュール実行 | 見送り | 手動ループの効果を確認してから opt-in で追加する |
| 「タグ精度 60% → 90%」等の数値目標 | 採用しない | 出典が個人の投稿 1 件で対照実験ではない。設計方針の参考に留める |

## 運用

1. Notion の Research Note に思いついたことを書く、または作業を進める
2. `/notion-sync` でミラーへ取り込む
3. `/notion-digest worklog` で作業ログ（コミット履歴込み）を Research Note へ追記する
4. 文献をまとめたいときは `/notion-digest literature`
5. 記録層が溜まってきたら `/notion-digest knowledge` で概念ノートへ切り出す

3 と 5 の比率が要点である。記録だけを溜めても「何を知っているか」には答えられず、記録なしに知識層だけ書こうとしても根拠が付かない。まず 3 のループを回し、同じ論点が複数の記録に現れたら 5 を実行する。

## 自動記録の構成

記録層のノートは launchd で自動生成する。**収集と要約を分けている**のが構成の要点で、収集はスクリプト、要約だけをモデルが行う。こうすると収集の正しさをスクリプト単体で検証でき、モデルの出力ぶれと切り離せる。

```
launchd（日次 00:05 / 週次 月曜 00:30）
  └─ notion_digest_agent.sh <daily|weekly>
       ├─ activity_digest.py     材料を集める（LLM を使わない）
       │    ├─ ~/Documents/Repository/*/.git      26 リポジトリのコミット
       │    ├─ ~/.claude/projects/**/*.jsonl      Claude Code CLI の ai-title
       │    └─ …/Claude/local-agent-mode-sessions Claude アプリの title + initialMessage
       ├─ 空なら何もせず終了（活動のない日にノートを作らない）
       ├─ notion_sync.py         既存語彙と前回ノートの把握のため先に同期
       ├─ claude --print         材料を要約して 1 行書く
       └─ notion_sync.py         書いた行をミラーへ降ろす
```

| ファイル | 役割 |
|---|---|
| `~/.claude/scripts/activity_digest.py` | 材料の収集。`--date` / `--since --until` / `--days` / `--pending N` / `--recorded` / `--format json` |
| `~/.claude/scripts/notion_digest_agent.sh` | 起動スクリプト。`daily` / `weekly` / `--dry-run` / `--date` / `--since --until` |
| `~/.claude/scripts/backfill_weekly.sh` | 過去を週次で遡る。`--list` / `--weeks N` / `--dry-run` |
| `~/.claude/scripts/notion_digest_{daily,weekly}_prompt.txt` | エージェントへの指示 |
| `~/.claude/scripts/com.lleoo.notion-{daily,weekly}-digest.plist` | launchd テンプレート |
| `~/.claude/scripts/install_notion_digest_launchd.sh` | 配置と再ロード。`--uninstall` で解除 |
| `~/Library/Logs/notion-digest/` | 実行ログ（30 日で間引く） |

### 設計上の判断

**なぜ生のユーザー発話を使わないか。** 1 日あたり中央値 13 万文字、最大 71 万文字あり、貼り付けたログが大半を占めて信号にならない。Claude Code が自動生成する `ai-title` と、アプリ側の `title` / `initialMessage` が同じ内容を数百文字で表す。`ai-title` が無いセッションだけ、最初の発話の冒頭 120 文字で代用する。

**なぜ稼働日をメッセージ単位で求めるか。** セッションの最終時刻 1 点で日付を決めると、**日をまたいだセッションが終了日にしか計上されず、開始日の作業が丸ごと消える**。長い作業ほど日をまたぐため、影響を受けるのは重要なセッションのほうである。実際に 07-31 では 342 往復と 395 往復の 2 セッションが落ち、その日が「人手による作業なし」と記録された。CLI は各メッセージの `timestamp`、アプリは `audit.jsonl` の `_audit_timestamp` から稼働日の集合を作り、**該当する日すべてに計上する**（`[日跨ぎ]` の印を付ける）。アプリ側は 189 件中 21 件が日をまたぐ。

**なぜ `agent-*.jsonl` を除外するか。** subagent のトランスクリプトであり、親セッションの内部作業である。独立した作業として数えると二重計上になる。781 件中 377 件がこれで、いずれも `ai-title` もユーザー発話も持たない。除外すると走査量もほぼ半減する。

**本文の先頭にタイトルの見出しを作らない。** `notion_sync.py` がミラー生成時に `# タイトル` を付与するため（`:659`）、本文側にも `heading_1` を置くと二重になる。Notion 上でもページタイトルの直下に同じ文字列が並ぶ。

**なぜ 1 日 1 行か。** プロジェクトごとに行を作ると、稼働 3〜4 プロジェクト × 365 日で年 1200 行を超え、一覧が使えなくなる。プロジェクトの別は本文の `## 動いたプロジェクト` で表す。

**なぜ 00:05 に前日ぶんか。** 23:55 に当日を書く方式では 23:55〜24:00 の作業が落ちる。日付が変わってから前日を確定させれば取りこぼしがない。スリープ中に逃した回は復帰時に 1 回だけ遅延実行される（launchd の標準挙動）。

**なぜ日次と週次でロックを共有するか。** 週次は日次が書いたノートをミラーから読むため、順序が入れ替わると束ね損なう。25 分の間隔はそのための余裕である。

**Claude アプリのセッションはローカルにある。** `local-agent-mode-sessions/**/local_<uuid>.json` に `title` / `initialMessage` / `lastActivityAt` / `userSelectedFolders` があり、同ディレクトリの `audit.jsonl` には全メッセージ本文もある。CLI 側のセッション ID とは重ならないため二重計上にならない。コミットの残らない作業（申請書・スライド・文献調査）はここにしか現れないため、記録の網羅性はこのソースに依存している。

### 無人実行が静かに壊れないための仕掛け

無人で動くものは、壊れても誰も気づかない。次の 4 つで「気づかないうちに記録が途切れる」経路を塞いでいる。

| 仕掛け | 何を防ぐか |
|---|---|
| **ロックの期限**（`LOCK_STALE_SECONDS` 90 分） | `kill -9` や強制再起動でロックが残ると、以後すべての実行が「進行中」と誤認してスキップし続ける。期限を超えたロックは奪って続行する。**これが無いと一度の異常終了で仕組みが恒久的に死ぬ** |
| **未記録日の自動補完**（`BACKFILL_DAYS` 7 日） | launchd は逃した起動を 1 回に集約するため、スリープが続くと間の日が永久に失われる。「前日」固定をやめ、未記録かつ活動のある日を古い順に埋める |
| **重複防止** | 手動実行と launchd が同じ日を二重に書くのを防ぐ。判定はミラーの `種別: 進捗` と `Date` で行うため、**同期の後**に行う必要がある |
| **macOS 通知** | 失敗時と、欠落が上限を超えたときに知らせる。週次の `## 知見候補` に件数があるときも通知し、人が Notion を開く動機を作る |

**CLI トランスクリプトは約 30 日で間引かれる。** 気づくのが遅れると会話の材料ごと失われるため、失敗の検知はコミットより会話の記録にとって重要である。`activity_digest.py --pending 30` で欠落を確認できる。

### シェルスクリプトの落とし穴（インストーラが機械的に弾く）

`"...（${VAR}）"` のように**変数の直後へ全角文字を置くと、bash が変数名の一部として解釈する**。`$LOCK_DIR）` は `LOCK_DIR）` という名前の変数と見なされ、`set -u` の下では未定義エラーになる。その分岐に入ったときだけ落ちるため、通常のテストでは気づきにくい。

波括弧 `${VAR}` で囲めば防げる。同じ誤りを 2 度作ったため、`install_notion_digest_launchd.sh` が配置前に全 `*.sh` を走査して弾くようにした（コメント行は対象外）。BSD grep は角括弧内の `\x` エスケープを解釈せず誤検知するので、判定は Python で行っている。

### 無人実行に必要なトークン

`~/.claude/.env` に 2 つ要る。どちらも `.gitignore` の対象である。

| キー | 用途 |
|---|---|
| `NOTION_TOKEN` | Notion MCP と `notion_sync.py` が共有する |
| `CLAUDE_CODE_OAUTH_TOKEN` | `claude setup-token` で発行する 1 年有効・サブスク枠のトークン。Keychain の OAuth より優先され、無人実行が 401 で落ちにくくなる。**API 従量課金にならない** |

## Enhanced Markdown の語彙

`PATCH /v1/pages/{page_id}/markdown` は素の Markdown に加えて Notion 固有のタグを解釈する。Research Management ページを `GET /v1/pages/{id}/markdown` で読み戻して実測した書式は次のとおり（**子要素はタブインデント**）。

```
<callout icon="/icons/document_gray.svg" color="gray_bg">
	**見出し**
	本文
</callout>
---
<columns>
	<column ratio="25"> … </column>
	<column ratio="75"> … </column>
</columns>
<details>
<summary>開閉する見出し</summary>
	中身
</details>
```

- `color` は `gray_bg` / `orange_bg` など。`icon` は `/icons/<name>_<color>.svg`
- Markdown テーブルは `<table header-row="true">` へ変換されて往復する
- **` ```mermaid ` は言語ごと保持され、Notion が図として描画する**
- **コードブロックの言語は必ず明示する。** 省くと誤検出される（言語なしの bash が `javascript` になった実例あり）。図や擬似コードは `text` を指定する
- レスポンスの `truncated` フラグで切り詰めを検出できる

## 大きな文書の投入

**分割は要らない。105KB・66,204 文字の Markdown を 1 リクエストで投入し、`truncated: false` で全量が入ることを実測した**（`python-bci-platform/docs/CODE_REVIEW.md`）。読み戻しても先頭・末尾とも欠落しない。

- 投入は `{"type": "replace_content", "replace_content": {"new_str": "…"}}`
- 本文をモデルの文脈へ通す必要はない。**スクリプトからこのエンドポイントへ直接 PATCH する**のが正しい。42 ノート 700KB を投入した実績がある
- `---` の前後には空行を置く。空行が無いと直前の行が setext 見出しとして解釈される

## 解説資料の置き場所

**解説資料の原文と清書版 HTML はミラーに一本化する。プロジェクトの `docs/` には置かない。** 以前は各リポジトリの `docs/` にも置いていたが、同じ資料が複数箇所に散らばってどれが最新か分からなくなった（`BrainProducts.html` が 5 箇所、`ANALYSIS.html` と `PROTOCOL.html` が 3 箇所ずつ）。

```
~/.notion-mirror/
├─ _md/<project>/docs/<name>.md              ← 原文（唯一の原本）
├─ _html/研究ノート_DB/知見/BrainProducts.html  ← 清書版（唯一の HTML）
├─ 研究ノート_DB/知見/2026-07-28-…-3afb6e7e.md  ← 同期が書く
└─ _manifest.json
```

- **先頭の `_` は「Notion 由来ではない、こちらが予約した領域」の印。** ミラー直下の名前は Notion のページ名が決めるため、印を付けないと同名ページができた瞬間に混ざる
- `_md/` は `<project>/docs/<name>.md` の相対パスをそのまま保つ。`overrides.json` のキー・`spec.json` の `primary`・ノートの「取り込み元」行がこの相対パスなので、ルートだけを移せば全部そのまま通る
- 清書版はミラーの相対パスを写して `_html/` へ置く（`_html/研究ノート_DB/知見/…`）
- **Notion はページ内で HTML/JS を描画できない。** ページ側にはパスを 1 行書くに留める。embed で外部ホスティングすると、ミラーには URL しか残らず grep 検索が効かなくなるため採らない

### ミラーは丸ごと消してよい場所ではなくなった

`_md/` に原本が入った以上、**`rm -rf ~/.notion-mirror` は使わない。** 作り直しは `notion_sync.py --full` で行う（manifest 記載のパスだけを取り直すので `_md/` と `_html/` は無傷）。

- ミラー直下を git リポジトリにし、`_md/` と `_html/` だけを追跡する。同期生成物（`研究ノート_DB/` などと `_manifest.json`）は `.gitignore` に入れる
- 原本が git で守られるので、誤って消しても取り戻せる

### 生成スクリプトと手書きの入力はミラーへ置かない

取り込みパイプラインは `~/.claude/scripts/notion_docs_ingest/` に置く（`overrides.json` の mermaid 指定と `hints.json` のコールアウト指定が手書きの入力にあたる）。ミラーは Notion と原文を写す場所であり、それらを加工する道具の置き場ではない。

## Notion の自動リンク化

**地の文の `foo.py` や `CLAUDE.md` は Notion がドメインとみなし `http://foo.py` へリンク化する。** クリックしても何も無い壊れたリンクが本文中に大量に生まれる（実測: 41 ノートで 477 箇所）。

- 対策はファイル名を**バッククォートで囲む**こと。ファイル名はコードなので意味的にも正しい
- **`src/mode/base_mode.py` のようなパスは全体を囲む。** Notion は途中の `mode.py` だけを切り出してリンク化する
- **境界判定に `\w` を使わない。** Python の `\w` は和文にもマッチするため「過剰なCLAUDE.md」「CLAUDE.mdの肥大化」を取りこぼす。ASCII の文字クラスで判定する
- 実在ドメイン（`claude.ai` `brainproducts.com` 等）のリンク化は正しい挙動なので触らない

## 既知の落とし穴

### multi_select の選択肢を更新しない

**`PATCH /data_sources/{id}` の `multi_select.options` は、渡したリストで既存のリストを丸ごと置き換える。** マージではない。省略した選択肢は消え、**その選択肢が付いていた全ページのタグも同時に失われる**。

さらに 1 回のリクエストで送れる選択肢は 100 件までという上限があるため、100 件を超える DB では「全件を送り返して安全に書き換える」ことが原理的にできない。Reference List は 339 件あったため、この方法は使えなかった。

実際にこれで Reference List 102 ページの Keywords を全消ししている。復旧できたのはミラーが変更前の状態を保持していたためで、**ミラーが唯一のバックアップとして機能した**。

- 選択肢の追加は**ページに値を書けば自動で行われる**。`PATCH /pages/{id}` で未知の名前を指定すると選択肢が作られる。スキーマ側を触る必要はない
- 選択肢の**名前は大小を区別せずに照合される**。`EMG` が存在する状態でページに `emg` を書くと既存の `EMG` に吸い寄せられる。正規化規則を守る理由はここにある
- どうしても旧名を消す必要があるときは「選択肢を小さいリストで作り直す → ミラーを正として全ページのタグを書き戻す」の順で行い、直後にページ単位で期待値と突き合わせて検証する
- `{"id": ..., "name": "新しい名前"}` を送っても改名されない。`id` があるとそちらが優先され、名前は無視される

### 環境変数が古いトークンを掴むことがある

`notion_sync.py` の探索順は 環境変数 → プロジェクトの `.env` → `~/.claude/.env` である。かつて `~/.zshrc` で `export NOTION_TOKEN` していた場合、その値が失効した後も**起動済みのセッションは古い値を保持し続ける**。`.env` を正しく直しても、そのセッションでは同期が「NOTION_TOKEN が無効です」で落ちる。

- 切り分け: `env -u NOTION_TOKEN python3 ~/.claude/scripts/notion_sync.py --check` が通れば環境変数が原因
- 恒久対策: `~/.zshrc` の `export` を消し、`~/.claude/.env` に一本化したうえで**セッションを開き直す**
- MCP サーバは別経路（`~/.claude.json` の設定）で起動するため、この状況では**MCP だけが動いて同期だけが落ちる**という紛らわしい症状になる

### `/search` のインデックス遅延

書き込み直後の `/notion-sync` で新規ページが取れないことがある。ページ自体は作成済みなので取りこぼしにはならない。少し置いて再実行する。

## トラブルシューティング

| 症状 | 原因と対処 |
|---|---|
| 終了コード 3 で何も起きない | `NOTION_TOKEN` が未設定。`.env` を確認する |
| 「NOTION_TOKEN が無効です」 | トークンの誤り、インテグレーションの削除、または**環境変数が古い値を保持している**（「既知の落とし穴」参照）。`env -u NOTION_TOKEN` を付けて切り分ける |
| MCP は動くのに `/notion-sync` だけ落ちる | 同上。両者はトークンの取得経路が異なる |
| ページのタグが一斉に消えた | `multi_select.options` を更新した。ミラーを正として書き戻す（「既知の落とし穴」参照） |
| 期待したページが同期されない | そのページがインテグレーションに共有されていない。Notion 側で接続する |
| 変換結果がおかしい | 変換ロジック更新後は `--full` で全件を取り直す |
| ミラーを作り直したい | `python3 notion_sync.py --full`。`rm -rf` は `_md/` の原本ごと消すので使わない |
| 「Databases with multiple data sources are not supported」 | 複数データソースの DB。スクリプトは 2025-09-03 で取り直すため通常は自動回復する |
| 書き込み直後の同期で新規ページが取れない | Notion の `/search` はインデックスに遅延がある（数十秒）。少し待って `/notion-sync` を再実行する。ページ自体は作成済みなので取りこぼしにはならない |
| MCP ツール (`mcp__notion__*`) が出てこない | 登録後に Claude Code を再起動していない、またはシェルで `NOTION_TOKEN` を export していない |
