# /notion-digest

Notion の **Research Note**（`研究ノート_DB`）へ行を追加します。読み取りはローカルミラー、書き込みは Notion MCP という方向を守ります。

## 追記先

| 項目 | 値 |
|---|---|
| データベース | `研究ノート_DB` |
| database ID | `30cb6e7e-18a2-81ef-814e-eabea30a4da1` |
| data source ID | `30cb6e7e-18a2-8144-b858-000b9f180525` |
| 場所 | Research Management ページ内「Research Note」見出しの直下 |

## 事前確認

1. ミラー（既定 `~/.notion-mirror/`）の存在を確認する。無ければ `python3 ~/.claude/scripts/notion_sync.py` を先に実行する
2. `python3 ~/.claude/scripts/notion_sync.py --check` で差分を確認し、あれば同期してから着手する（既存 Keywords の把握に必要）
3. 「NOTION_TOKEN が無効です」で落ちたら `env -u NOTION_TOKEN` を付けて再実行する（古い環境変数を掴んでいる。`notion-knowledge-base` skill の `reference.md` 参照）

## 自動記録との関係

日次・週次の記録層ノートは **launchd が自動で書きます**（毎日 00:05 に前日ぶん、月曜 00:30 に直近 7 日）。本コマンドの `worklog` は、その自動記録を待たずに手動で残したいときや、任意期間をまとめたいときに使います。

自動記録の構成は `notion-knowledge-base` skill の `reference.md`「自動記録の構成」を参照してください。

## モード: worklog（既定）

作業・検討・判断を記録層のノートとして残します。**特定のプロジェクトに閉じず、全リポジトリを対象にします。**

| ステップ | 処理 |
|---|---|
| 1 | 材料を集める。`python3 ~/.claude/scripts/activity_digest.py --date <対象日>`（期間なら `--since --until`）。コミット・Claude Code CLI・Claude アプリの 3 ソースが揃う |
| 2 | 出力が空なら**記録しない**。活動のない日にノートを作らない |
| 3 | 直前の記録層ノートを特定する。ミラーの `研究ノート_DB/進捗/` `研究ノート_DB/開発/` から最新のものを取り、その `notion_id` を `関連ノート` に入れる |
| 4 | 材料を読んで記録層の骨格に沿って本文を構成する |
| 5 | プロパティを組み立てる（後述） |
| 6 | 内容を提示して承認を得てから `mcp__notion__API-post-page` で行を追加する |
| 7 | `python3 ~/.claude/scripts/notion_sync.py` でミラーへ反映する。取得 0 件なら Notion のインデックス待ちなので、少し置いて再実行する |

**コミットハッシュ・件名の羅列を本文に書かない。** git にあるものの二重管理で、読み返す価値がありません。`## 動いたプロジェクト` にはプロジェクト名と一行要約だけを書き、何をしたかは `## やったこと` が担います。

**コミットの無い作業を落とさない。** 申請書・スライド・文献調査・打ち合わせ準備などは Claude アプリのセッションにしか現れません。`activity_digest.py` はこれを拾うので、材料に出てきたら必ず記録に含めてください。

**自動実行の繰り返しは 1 行に畳みます。** 同一プロジェクトで同じ内容のセッションが複数回現れる場合（定期実行される文献要約など）は人の作業ではないので、「文献要約の自動実行が N 件を追加」のようにまとめます。

**詰まっている点が新たに出たら、`種別: 課題` の行として別に起こします。** 作業ログの中に埋めたままにすると、後から追えなくなります。解決したときは解決先のノートを `関連ノート` に張ります。ただし**無人実行では課題の起票を行いません**（判断を要するため）。

## モード: literature

ミラー内のノートを横断して整理し、まとまった知見として残します。種別は `文献`、本文は知識層の骨格を使います。

| ステップ | 処理 |
|---|---|
| 1 | ミラーを `Grep` で走査し、対象ノート（`Reference-List/` の論文ノートなど）を絞り込む |
| 2 | 該当ファイルを `Read` し、共通する論点・対立する主張・空白領域を抽出する |
| 3 | 出典を必ず添える。読んだ論文は `関連文献` にも入れる |
| 4 | 以降は worklog と同じくプロパティを組み立て、承認を得てから追加・同期する |

**元ノートに書かれていない結論を足さない。** 判断に迷う内容は `## 未解決` に残してください。

## モード: knowledge

溜まった記録層のノートから、**そのリポジトリを離れても価値が残る主張**を概念ノートとして切り出します。

| ステップ | 処理 |
|---|---|
| 1 | ミラーの `研究ノート_DB/` から記録層（`層: 記録`）を走査し、複数の記録に繰り返し現れる論点を拾う |
| 2 | 主張として言えるところまで固まっているものだけを候補にする。1 回しか現れていない話は次の機会に回す |
| 3 | 候補ごとに、タイトル（完全な主張）・根拠・限界・出典を組み立てる |
| 4 | 候補の一覧を提示し、**どれを切り出すか承認を得る** |
| 5 | `種別: 知見`（または `アイデア`）で行を追加し、`関連ノート` に元の記録層ノートを入れる。**元の記録層ノート側にも書き返す**（`関連ノート` は単方向） |
| 6 | 同期する |

**根拠のない主張を作らない。** 元の記録に数値・観測・引用がないなら、それは知見ではなくまだアイデアです。`種別: アイデア` にしてください。

## プロパティの作り方

### 種別

そのノートが何の記録かを 1 つ選びます。**新しい種別を作らない。**

| 層 | 種別 | 使う場面 |
|---|---|---|
| 記録 | `進捗` | 作業の進み具合 |
| 記録 | `開発` | 実装・コーディング |
| 記録 | `実験` | 実験の実施・結果 |
| 記録 | `議論` | MTG・相談の結果 |
| 記録 | `日常` | 日々の雑記 |
| 記録 | `メモ` | 一時的な記録 |
| 知識 | `知見` | 根拠を伴って言える主張 |
| 知識 | `文献` | 論文の読解・整理 |
| 知識 | `アイデア` | 着想。まだ根拠が付いていないもの |
| 課題 | `課題` | 詰まっている点・TODO |

層は概念であって、プロパティとしては持ちません（`種別` から一意に決まるため）。

### Title

**短くします。** 日付は `Date` が持つので入れません。副題・修飾・根拠は `概要` と本文へ逃がし、「―」で副題をつなげません。

| 層 | 上限 | 例 |
|---|---|---|
| 記録・課題 | **20 文字** | `転移学習の analysis 統合` / `MRI 実験のクラス化` |
| 知識 | **30 文字** | `被験者間 EEG 分類は古典と深層が同水準` |

知識層は**完全な主張**にしますが、主張を保ったまま最短にします。削って不完全な文になったら削りすぎです。

- 避ける: `転移学習について`（主張になっていない）
- 避ける: `fit() がモデルを再構築する実装では、fit 前の重みロードは転移にならない`（40 文字。長い）
- 目指す: `fit 前の重みロードは転移にならない`（19 文字。主張は保たれている）

複数プロジェクトが動いた日は、最も比重の大きいものを Title にし、残りは概要と本文で表します。「複数プロジェクトの作業」のような中身のない題名にしません。

### 概要

1〜2 文の要約。Notion の一覧ビューで中身が見えるようにするための欄です。本文の繰り返しではなく、**読まなくても何の記録か分かる**ように書きます。

### Date

記録層は対象日、知識層は初版作成日。`YYYY-MM-DD` 形式。

### Keywords

**トピック語だけ**を 2〜5 個。種別語は入れません（`種別` プロパティが持つため）。

語彙は Reference List と共有します。**正規化規則は 小文字・ハイフン区切り・英語**（`EEG` ではなく `eeg`、`運動イメージ` ではなく `motor-imagery`）。Notion は選択肢名の大小を区別せずに照合するため、規則を外すと同義語が静かに増えます。

1. `grep -h "^Keywords:" ~/.notion-mirror/Reference-List/*.md` で既存語彙を集める
2. 3 回以上出現するコア語彙（`vr` `eeg` `bci` `haptics` `pseudo-haptics` `motor-imagery` `embodiment` `presence` など約 37 語）から優先して選ぶ
3. 1〜2 回しか出現しない裾野語は、既存として使ってよいが**候補として提示しない**
4. 既存語のどれとも異なる新概念のときだけ新語を提案し、**承認を得てから**追加する

### relation

すべてミラー上の grep で特定します。追加の API 読み取りは不要です。

| プロパティ | 埋め方 |
|---|---|
| `関連文献` | 本文に出た論文名・概念で `~/.notion-mirror/Reference-List/` を Grep し、一致したファイルの `notion_id` を入れる |
| `関連ノート` | 直前の記録層ノートの `notion_id`（記録の連鎖を切らさない）。knowledge モードでは切り出し元の記録ノート |
| `関連MTG` | 当日の議事録が `ミーティング議事録_DB/` にあれば、その `notion_id` |

`関連ノート` は**単方向**です。張ったら相手ページの現在値を `mcp__notion__API-retrieve-a-page` で読み、そこへ追加して `mcp__notion__API-patch-page` で書き戻します。現在値を読まずに書くと既存のリンクが消えます。

### アイコン

作成時に必ず指定します。`mcp__notion__API-post-page` の引数として properties と並べて `{"type": "icon", "icon": {"name": ..., "color": ...}}` を渡します。

| 種別 | name / color |
|---|---|
| `進捗` `開発` `実験` `議論` `日常` `メモ` | `document` / gray |
| `知見` | `light-bulb` / yellow |
| `文献` | `book` / brown |
| `アイデア` | `stars` / orange |
| `課題` | `warning` / red |

## 本文の骨格

種別ごとに見出しを固定します。同じ見出しで書かれた記録のほうが確実に引け、`Grep "^## 詰まっている点"` のような横断抽出も効きます。

| 層 | 見出し |
|---|---|
| 記録（日次） | `## やったこと` / `## 動いたプロジェクト` / `## 決めたこと` / `## 詰まっている点` |
| 記録（週次） | `## 今週の要点` / `## 進んだこと` / `## 詰まっていること` / `## 知見候補` |
| 知識 | `## 主張` / `## 根拠` / `## 限界・反証` / `## 出典` / `## 未解決` |
| 課題 | `## 症状` / `## 試したこと` / `## 次の一手` |

`## 動いたプロジェクト` はプロジェクト名と一行要約だけです。コミットハッシュを書きません。

知識層の `## 限界・反証` を空にしないでください。反証条件を書けない主張は、まだ主張になっていません。

## 規約

- 書き込み先は常に Notion。ミラーのファイルを直接編集しない（次の pull で失われる）
- **承認の要否は層で分かれる**
  - 記録層: 対話実行時は内容を提示してから書く。**無人実行時は承認不要**
  - 知識層・新規トピック語: **常に承認制**。無人エージェントには作らせない
- 憶測で埋めない。コミット履歴や元ノートで裏が取れない内容は書かない
- 1 回の実行で追加する行は 1 件を基本とする。複数必要なら件数を提示して確認する（worklog に伴う `課題` の起票、knowledge の複数切り出しは例外だが、いずれも承認を取る）
- **`multi_select` の選択肢をスクリプトから書き換えない。** リスト全体の置き換えになり、全ページのタグが消える。選択肢はページに値を書けば自動で作られる
