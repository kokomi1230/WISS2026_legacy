# Notion 知識ベース連携 (notion-knowledge-base)

Notion を長期保存先、ローカルミラーを走査対象、Claude Code を操作側とする知識スタックの入口ガイドと規約を提供する。本スキルは「どちらの経路で読み、どちらへ書くか」の振り分けと、ノートの層・種別・Keywords の規約に集中する。DB 構成・セットアップ手順・設計判断は同ディレクトリの `reference.md` にある。

## いつ発火させるか

- Notion の知識ベースへ書く / から読む要求
- 過去の調査メモ・ノート・成果物を横断的に探す
- Research Note への作業ログ・知見の追記
- 「前に調べた」「以前まとめた」など、セッションを超えた文脈の参照

## 中心となる制約: 読みはローカル、書きは Notion

```
Notion（人間が書く・探す・読む・見た目）
  │  /notion-sync が REST API で pull（一方向・増分）
  ▼
~/.notion-mirror/（全プロジェクト共通。同期が書く領域は派生物・手編集禁止）
  │  Grep / Read で走査（低コスト）  ← 読み取りは必ずこちら
  ▼
整理・要約・照合
  │  Notion MCP で書き戻し    ← 書き込みは必ずこちら
  ▼
Notion  →  次の /notion-sync でミラーへ反映
```

MCP 経由の読み取りはページごとに本文をコンテキストへ載せるため、**コーパスの走査にこれを使わない**。ミラーであれば全件を `Grep` で絞ってから必要な箇所だけ読めるので、コーパス全体を見渡した上で判断する状態を安価に作れる。

## 3 層モデル

研究ノート_DB の `種別`（select）で層が決まる。層は概念であって、プロパティとしては持たない（`種別` から一意に決まる冗長な値になるため）。

| 層 | 種別 | 性格 | タイトル |
|---|---|---|---|
| 記録 | `進捗` `開発` `実験` `議論` `日常` `メモ` | 日付に紐づく。追記のみで、後から書き換えない | 名詞句 |
| 知識 | `知見` `文献` `アイデア` | 概念単位。後から何度でも書き換える | **完全な主張** |
| 課題 | `課題` | 未解決の論点。解決したら解決先を `関連ノート` でつなぐ | 名詞句 |

種別は上の 10 語がすべてである。**新しい種別を勝手に作らない。**

### タイトルは短くする

| 層 | 上限 | 例 |
|---|---|---|
| 記録 | **20 文字** | `転移学習の analysis 統合` / `MRI 実験のクラス化` |
| 知識 | **30 文字** | `被験者間 EEG 分類は古典と深層が同水準` |
| 課題 | **20 文字** | 名詞句 |

日付は `Date` が持つのでタイトルに入れない。副題・修飾・根拠は `概要` と本文へ逃がす。「―」で副題をつなげない。

知識層のタイトルは**完全な主張**にする（Matuschak の titles-as-API）。タイトルだけで参照でき、他のノートから引用できる状態にする。ただし主張を保ったまま最短にする。削って不完全な文になったら削りすぎである。

- 避ける: `転移学習について`（主張になっていない）
- 避ける: `fit() がモデルを再構築する実装では、fit 前の重みロードは転移にならない`（40 文字。長い）
- 目指す: `fit 前の重みロードは転移にならない`（19 文字。主張は保たれている）

### 記録層と知識層の切り分け

作業ログに書いた内容のうち、**そのリポジトリを離れても価値が残る主張**は知識層へ切り出す。切り出したら `関連ノート` で双方向につなぐ（単方向のプロパティなので、両方のページへ書く）。

ソースコードそのもの・git 差分・そのリポジトリ固有の規約は知識層に書かない。それらは git と `CLAUDE.md` の担当である。

**ただし `docs/` に置かれた設計文書・調査文書・手順書は別扱いで、全文取り込みの対象である。** これらはコードではなく読み物であり、リポジトリを離れても読む価値がある。扱い方は「ドキュメント取り込みノート」を参照。

## 経路の使い分け

### 読み取り

| やりたいこと | 使うもの |
|---|---|
| 条件に合うノートを横断的に探す | ミラーに `Grep`。frontmatter に Notion のプロパティがそのまま入るため `Grep "^種別: 課題"` や `Grep "^Keywords: .*bci"` で DB のフィルタ相当の絞り込みができる |
| 層で絞る | `Grep "^種別: 知見"` のように種別を並べる、またはミラーの `研究ノート_DB/<種別>/` を `Glob`（種別がディレクトリになる） |
| ノート本文を読む | ミラーのファイルを `Read` |
| 固定見出しを横断抽出する | `Grep "^## 未解決" -A 5` のように見出し単位で拾う |
| ディレクトリ構成を把握する | ミラーに `Glob` |
| ミラーに無い / 同期直後の内容を確認する | `mcp__notion__API-retrieve-page-markdown`（ピンポイントのみ） |
| DB のスキーマ・選択肢を確認する | `mcp__notion__API-retrieve-a-data-source` |
| ミラーが古い疑いがある | 先に `/notion-sync --check` |

### 書き込み

| やりたいこと | 使うもの |
|---|---|
| DB に行を追加する | `mcp__notion__API-post-page`（parent に data source を指定） |
| 既存ページのプロパティを更新する | `mcp__notion__API-patch-page` |
| 既存ページの本文を編集する | `mcp__notion__API-update-page-markdown` |

書き込み後は `/notion-sync` を実行してミラーへ反映する。

**MCP は API キー方式のローカルサーバ**（`@notionhq/notion-mcp-server`）で、同期スクリプトと同じ `NOTION_TOKEN` を使う。ツールは `mcp__notion__API-*` の名前空間。OAuth 版のコネクタ（`mcp__claude_ai_Notion__*`）は使わない。

## 規約

- **同期が書いた領域を手で編集しない。** 派生物であり次の pull で上書きされる。取り直しは `--full` で行う
- **`rm -rf ~/.notion-mirror` は使わない。** `_md/` に解説資料の原本が入っており、消すと失われる（「解説資料の置き場所」参照）
- **ローカルから Notion への push は行わない。** 書き手を 1 方向に保つことで競合を構造的に排除している
- **MCP の読み取りを使う場合はサーバ側で絞る。** `mcp__notion__API-query-data-source` のフィルタを使い、取得件数を最小にする。ワークスペース全体の走査を試みない
- **セッション開始時に自動で読み込まない。** 明示的に要求されたときだけミラーを参照する
- **multi_select の選択肢をスクリプトから書き換えない。** リスト全体の置き換えになり、省略した選択肢と全ページのタグが消える。仕組みと復旧手順は `reference.md` の「既知の落とし穴」を必ず読むこと

## Keywords の付け方

`Keywords`（multi_select）には**トピック語だけ**を入れる。種別は `種別` プロパティが持つので、ここには入れない。1 ノートあたり 2〜5 個を目安にする。

### 語彙は Reference List と共有する

研究ノート_DB と Reference List DB は**同じ語彙**を使う。別々の語を使うと「この論点について何を知っているか」を引くのに 2 回 grep することになり、しかも取りこぼす。

**正規化規則**: 小文字・語の区切りはハイフン・英語。`EEG` ではなく `eeg`、`運動イメージ` ではなく `motor-imagery`、`Motor Imagery` ではなく `motor-imagery`。Notion の選択肢は名前の大小を区別せずに照合するため、この規則を外すと同義語が静かに増える。

### 決め方

1. **既存語彙を集める** — `grep -h "^Keywords:" ~/.notion-mirror/Reference-List/*.md` で実際に使われている語を列挙する。ミラーが古い疑いがあるときは `mcp__notion__API-retrieve-a-data-source` で選択肢一覧を取る
2. **コア語彙を優先する** — 3 回以上出現する語（`vr` `eeg` `bci` `haptics` `pseudo-haptics` `weight-perception` `embodiment` `motor-imagery` `presence` `neurofeedback` `erp` `neural-decoding` `hci` など約 37 語）から選ぶ。1〜2 回しか出現しない裾野語は、既存として尊重するが**候補として提示しない**
3. **既存語へ寄せる** — 候補が既存語と同義または十分近ければ既存語を使う。表記ゆれ（全角半角・英日・略語）も同義として扱う
4. **新語は承認を取る** — 既存語のどれとも異なる新しい概念のときだけ提案し、**ユーザーの承認を得てから**追加する。承認なしに語彙を増やさない

4 番目を省くと自由生成と変わらなくなる。

## 本文の骨格

種別ごとに見出しを固定する。同じ見出し・同じ順序で書かれた記録のほうが確実に引ける。加えて見出し単位の横断抽出（`Grep "^## 詰まっている点"`）が効くようになる。

| 層 | 見出し |
|---|---|
| 記録（日次） | `## やったこと` / `## 動いたプロジェクト` / `## 決めたこと` / `## 詰まっている点` |
| 記録（週次） | `## 今週の要点` / `## 進んだこと` / `## 詰まっていること` / `## 知見候補` |
| 知識 | `## 主張` / `## 根拠` / `## 限界・反証` / `## 出典` / `## 未解決` |
| 課題 | `## 症状` / `## 試したこと` / `## 次の一手` |

- **コミットハッシュ・件名の羅列を本文に書かない。** git にあるものの二重管理であり、読み返す価値がない。`## 動いたプロジェクト` にはプロジェクト名と一行要約だけを書き、何をしたかは `## やったこと` が担う
- 知識層の `## 限界・反証` を空にしない。反証条件を書けない主張は、まだ主張になっていない

**この見出し表は人が書き下ろすノート専用である。** 既存の `.md` を取り込むノートには適用しない（下記）。

## ドキュメント取り込みノート

`docs/` の Markdown を Notion ノートにするときは、**原文を要約せずそのまま移す**。骨格は次に固定する。

```
<callout icon="/icons/document_gray.svg" color="gray_bg">
	**<原文の H1>**
	<1〜2 文で何の文書か。DB の `概要` プロパティと同じ文でよい>
	出典: `<repo>/docs/<file>.md`（<行数> 行 / <サイズ>）
	清書版 HTML: `~/.notion-mirror/_html/…`   ← 用意した場合のみ
</callout>

---

（原文の本文。H1 だけ落とし、H2 以下の見出し・段落・表・コードブロック・箇条書きはそのまま）

---

## 取り込み元

- `<repo>/docs/<file>.md`
```

守ること。

- **要約しない。言い換えない。まとめない。** 文字数の上限を設けない
- **削ってよいのは重複だけ**。同じ表・同じ段落が 2 回目に出たら「（§X 参照）」へ置換し、別ノートと重なる説明は片方に残して `関連ノート` でつなぐ。**判断に迷う箇所は残す**
- `## 取り込み元` を必ず置く。再実行時の重複判定に使う。同一内容の複製ファイルは 1 ノートへ統合し、全パスをここへ併記する
- 本文はモデルの文脈を通さず**スクリプトから `PATCH /v1/pages/{page_id}/markdown` へ投げる**。105KB を 1 リクエストで投入できることを実測済み（`reference.md` 参照）
- **地の文のファイル名はバッククォートで囲む。** 囲まないと Notion が `foo.py` をドメインとみなして壊れたリンクにする（`reference.md`「Notion の自動リンク化」参照）

実装は `~/.claude/scripts/notion_docs_ingest/` にある。`build_spec.py` → `verify_fidelity.py` → `ingest.py` → `md2html.py` の順に流す。

## 図表化

読みやすさは Notion のブロックで作る。**Notion はページ内で HTML/JS を描画できない**ため、テンプレート HTML をそのまま埋め込むことはできない。

| 原文の要素 | Notion での扱い |
|---|---|
| ASCII の流れ図・構成図 | **mermaid を直前に置き、原文のコードブロックも残す**。ノード名は原文の語をそのまま使う |
| ディレクトリツリー・ファイル一覧・API 一覧 | mermaid にしない。コードブロックのまま（図にすると読みにくくなる） |
| 表 | Markdown テーブルのまま書けば Notion テーブルになる |
| コードブロック | **言語を必ず明示する**。省くと Notion が誤検出する |
| 文章で書かれた処理の流れ | 高々 1〜2 個まで mermaid を足してよい。増やしすぎない |

清書版の HTML が要るときは `explainer-doc-html` skill で作り、`~/.notion-mirror/_html/` へミラーの相対パスを写して置く。Notion 側にはそのパスを冒頭 callout へ 1 行書くに留める。

## リンクの張り方

| プロパティ | 相手 | 何を入れるか |
|---|---|---|
| `関連文献` | Reference List | 依拠した論文、およびその回に調べた論文 |
| `関連ノート` | 研究ノート_DB（自己参照・**単方向**） | 記録の連鎖、記録層 → 切り出した知識層、知識層どうしの接続 |
| `関連MTG` | ミーティング議事録_DB | 出所の議事録 |

**`関連ノート` は単方向なので、張ったら相手側にも書き返す。** 相手ページの現在値を `mcp__notion__API-retrieve-a-page` で読み、そこへ追加してから `mcp__notion__API-patch-page` で書き戻す。現在値を読まずに書くと既存のリンクが消える。

リンク先はミラー上の grep で特定する。追加の API 読み取りは要らない。確度で扱いを分ける。

| 経路 | やり方 | 確度 |
|---|---|---|
| コミット由来 | `activity_digest.py` が `docs: add <bibkey> to references` から bibkey を取り、Reference List の Bibtex と突き合わせて `notion_id` まで解決する。材料の `## 関連する文献` に出たものはそのまま入れてよい | 確定 |
| その回に調べた文献 | セッション表題や依頼文に出た論文名・著者名で `grep -il "<名前>" ~/.notion-mirror/Reference-List/*.md` | 判断あり |
| 議事録 | 対象日の `ミーティング議事録_DB/` を見る | 確定 |

**曖昧な一致は入れない。** トピックが近いだけの論文を張らず、名前・著者・タイトルが実際に材料へ現れたものに限る。誤ったリンクは無いリンクより悪い。

### アイコン

作成時に必ず明示する。記録層は `document`/gray、`知見` は `light-bulb`/yellow、`文献` は `book`/brown、`アイデア` は `stars`/orange、`課題` は `warning`/red。書式と検証済みの名前は `reference.md` の「アイコン」を参照。

ミラーの frontmatter では relation は**ページ ID の配列**になる。ID からファイルへは `~/.notion-mirror/_manifest.json`（`page_id -> {path, last_edited_time}`）で解決する。

## 健全性チェック

ミラーへの grep だけで済む。定期的に、あるいは `/notion-digest` の前に流す。

| 見るもの | やり方 |
|---|---|
| 種別のないノート | `Grep -L "^種別:" ~/.notion-mirror/研究ノート_DB/` |
| 語彙から外れたトピック語 | `Keywords:` を集計し、Reference List 側の語彙に無い語を洗い出す |
| 放置された課題 | `状態: 対応中` かつ `last_edited_time` が 30 日以上前 |
| 孤立した知識ノート | `研究ノート_DB/知見/` `/文献/` `/アイデア/` で `関連ノート` も `関連文献` も持たないもの |
| 記録の欠落 | `python3 ~/.claude/scripts/activity_digest.py --pending 30` で未記録かつ活動のある日を出す |

- **`Grep` / `Glob` ツールを使い、シェルのグロブに頼らない。** 知識層のタイトルは主張なので `fit()` のような括弧を含むことがあり、`for f in $(find …)` の類は zsh のグロブ展開で落ちる
- 「語彙から外れたトピック語」は、**承認したばかりの新語が Reference List でまだ使われていない**場合にも出る。これは異常ではない。同じ語が論文側にも付いた時点で消える

## 自動記録との役割分担

記録層は **launchd で自動記録される**。知識層は人が判断して切り出す。この境界を越えない。

| | 日次・週次記録（記録層） | 知見記録（知識層） |
|---|---|---|
| いつ | 毎日 00:05（前日ぶん） / 月曜 00:30（直近 7 日） | 同じ論点が複数の記録に現れたとき |
| 起動 | launchd → `~/.claude/scripts/notion_digest_agent.sh` | 人が `/notion-digest knowledge` を叩く |
| 判断 | 不要（機械的な集約） | 必要（何が主張に値するかの判断） |
| 承認 | **不要** | **必須** |

- **無人エージェントは知識層ノートと新規トピック語を作らない。** 自動化すると根拠のない主張が量産され、コーパスの信頼性が落ちる
- 週次ノートの `## 知見候補` が、人が切り出すときの入口になる
- 対話中に記録層のノートを書くときは、内容を提示してから書く（無人実行時のみ承認不要）
- 活動が無い日はノートを作らない。`activity_digest.py` が空を返し、エージェントは何もせず終了する

材料の収集は `~/.claude/scripts/activity_digest.py` が行う（コミット / Claude Code CLI / Claude アプリの 3 ソース）。詳細は `reference.md` の「自動記録の構成」を参照。

## 記憶層の境界

判断基準は「**そのリポジトリを離れても価値が残るか**」。残るなら Notion、残らないならリポジトリ内（`CLAUDE.md` / `.claude/MEMORY.md` / `tasks/`）。

Notion に書かないもの: ソースコードそのもの・git 差分・リポジトリ固有の規約。例外が 2 つある。

- **作業ログに含めるコミット履歴**は「何をしたか」の記録として `/notion-digest worklog` が本文に入れる
- **`docs/` の設計文書・調査文書・手順書**は全文取り込みの対象。読み物であってコードではない（「ドキュメント取り込みノート」参照）

## 関連アセット

- `/notion-sync` — ミラーの生成・更新（`~/.claude/scripts/notion_sync.py`）
- `/notion-digest` — Research Note への追記（`worklog` / `literature` / `knowledge` の 3 モード）
- `reference.md`（同ディレクトリ）— DB 構成・スキーマ・セットアップ手順・設計判断・既知の落とし穴
