# Notion 知識ベース連携 ― 追加機能の解説

Claude Code が過去の調査メモや作業文脈をセッションをまたいで参照できるようにする仕組みを追加しました。Notion に蓄積した知識をローカルの Markdown へ一方向で取り込み、エージェントはそのコピーを走査します。この資料は「何を追加し、なぜその形にしたか」を説明します。

セットアップ手順・データベースのプロパティ定義・トラブルシューティングは `~/.claude/skills/notion-knowledge-base/reference.md` にあります。

---

## 1. 何が問題だったか

新しい会話を開くたびに、前回までの文脈は失われます。プロジェクトの背景、これまでの判断、調べた内容を毎回説明し直すことになります。

Notion にノートを溜めていても、この問題は解決しません。**ノートが存在することと、エージェントがそれを読めることは別**だからです。

MCP 経由で Notion を読むこともできますが、これはコーパス全体の走査には向きません。

| 読み方 | 何が起きるか |
|---|---|
| MCP でページを取得 | ページ本文がモデルのコンテキストを通過する。ページ数に比例してトークンを消費する |
| MCP でワークスペースを走査 | ページネーションを繰り返し、全体を見渡す前にコンテキストが埋まる |
| ローカルファイルを Grep | 一致箇所だけが返る。全件を絞ってから必要な箇所を読める |

つまり、**Notion に知識があること自体は問題なく、それをエージェントが安く走査できないことが問題**でした。

---

## 2. 追加した機能

6 つの資産を追加しました。

| 資産 | 種類 | 役割 |
|---|---|---|
| `.claude/scripts/notion_sync.py` | スクリプト | Notion をローカル Markdown へ一方向 pull。増分同期・削除追従つき |
| `/notion-sync` | コマンド | 上記スクリプトの実行入口 |
| `/notion-digest` | コマンド | 未整理ノートの構造化（`inbox`）と週次ダイジェスト生成（`weekly`） |
| `notion-knowledge-base` | skill | どちらの経路で読み、どちらへ書くかの振り分け規約 |
| `~/.claude/skills/notion-knowledge-base/reference.md` | ドキュメント | 設計・データベース構成・セットアップ手順の正典 |
| `CLAUDE.md` の記憶層の境界 | 規約 | どの知見をどこに書くかの振り分け基準 |

### 記憶層の境界を決めたことが本体

このリポジトリには既に記憶系が 4 つありました（`CLAUDE.md` の規約、`.claude/MEMORY.md` の学習履歴、ハーネス個人メモリ、`tasks/` の作業チケット）。境界を決めずに 5 つ目を足すと、「どこに書けばいいのか」が毎回分からなくなります。これは今回解決しようとしている問題そのものを悪化させます。

そこで判断基準を 1 つに絞りました。**このリポジトリを離れても価値が残るか。** 残るなら Notion、残らないならリポジトリ内です。

コード・差分・リポジトリ固有の規約は Notion に書きません。それは git と `CLAUDE.md` の担当です。

## 3. 仕組み

Notion とローカルファイルを、それぞれ得意な側に寄せています。Notion は検索性・可読性・見た目に優れ、ローカルファイルは走査コストが小さい。

```
Notion（人間が書く・探す・読む）
  ↓  notion_sync.py が REST API で pull（一方向・増分）
~/.notion-mirror/（全プロジェクト共通。同期が書く領域は派生物・手編集禁止）
  ↓  Grep / Read で走査
整理・要約・照合
  ↓  Notion MCP で書き戻し
Notion  →  次の pull でミラーへ反映
```

読み取りはミラー、書き込みは Notion。この向きを固定しています。

### 一方向に限定した理由

双方向同期には ID マッピング、競合解決、Notion ブロックと Markdown の非可逆変換（トグル・コールアウト・データベース・リレーション・コメント）、リネームと削除の検出が必要になり、実装量とデータ損失のリスクが跳ね上がります。

同期が書いた領域を「いつでも取り直せる派生物」と定義し、手で編集しないと決めれば、**競合は構造的に発生しません**。書き手が常に 1 方向だからです。

その代わり、その領域のファイルを直接編集しても次の pull で失われます。編集は Notion 側で行ってください。

この約束が及ぶのは同期が書いた領域だけです。`_` で始まる直下のディレクトリ（`_md/` の解説資料原文・`_html/` の清書版）は同期の管理外で、手で編集してよく、取り直しの対象にもなりません。原本が入っているため `rm -rf ~/.notion-mirror` は使わず、作り直しは `notion_sync.py --full` で行います。

### MCP ではなく REST API で取り込む理由

MCP 経由で取り込むと、全ページの本文がモデルのコンテキストを通過します。取り込み処理そのものが、ミラー化の目的であるトークン削減を打ち消してしまいます。

REST API を直接叩くスクリプトなら本文はコンテキストを一切通らず、処理も速く、将来の自動実行にも乗せられます。標準ライブラリだけで書いてあるため追加インストールは不要です。

### ミラーを全プロジェクト共通にした理由

知識コーパスはリポジトリ単位ではなく 1 つです。既定の置き場所は `~/.notion-mirror/`（`NOTION_MIRROR_DIR` で変更可）で、どのプロジェクトからも同じコーパスを参照します。蓄積がリポジトリをまたいで効きます。

### 取り込みの安全側の作り

- 共有されたページだけが同期対象です。共有範囲がそのまま同期範囲の制御になります
- ページの列挙は毎回全件、本文の取得だけを更新差分に絞ります。削除の検出を保ちながら通信量を抑えるためです
- 未対応のブロック種別は `<!-- 未対応ブロック: type -->` として残します。内容を黙って落とさないことを優先しています
- 取得中に共有が外れたページはスキップし、既存ファイルを空の本文で上書きしません

## 4. 使い方

### 準備

1. Notion で内部インテグレーションを作成する（権限は読み取りのみで足ります）
2. 取り込みたいページ・データベースをそのインテグレーションに共有する
3. `.env` に `NOTION_TOKEN` を書く（`.gitignore` 対象です）

トークンが未設定のときは API を叩かずに手順を案内して終了します。

環境変数の `NOTION_TOKEN` が `.env` より優先されます。古いトークンがシェルに残っていると、`.env` に新しい値を書いても効きません。

### 運用ループ

1. Notion のノートに思いついたことを書く（種別＝受信箱、状態＝未整理）
2. `/notion-sync` でミラーへ取り込む
3. `/notion-digest inbox` で未整理ノートを整理し、プロジェクトへ引き上げる
4. 週に一度 `/notion-digest weekly` で週次ダイジェストを作る

まず受信箱の 1 ループだけを回してください。安定してから対象を広げます。最初から全部を自動化しようとすると、空のデータベースが増えるだけになります。

### 取り込んだ後にできること

frontmatter に Notion のプロパティがそのまま入るため、データベースのフィルタに相当する絞り込みが Grep でできます。

```
Grep "状態: 未整理"      # 未整理のノートだけ
Grep "種別: 読書メモ"    # 読書メモだけ
```

## 5. まとめ

- Notion に知識があることと、エージェントが安く読めることは別の問題
- ローカルミラーを置くと、コーパス全体を見渡した上で判断できるようになる
- 一方向に限定することで、競合解決を実装せずに済ませている
- 同期が書いた領域は派生物。手で編集せず、いつでも取り直してよい（`_md/` `_html/` は管理外で原本が入る）
- 記憶層の境界を決めることが、同期機構と同じくらい重要

## よくある疑問

**ミラーを消してしまったら？**
`/notion-sync` を実行すれば全件を取り直します。ミラーは派生物なので、消えて困るものはありません。

**なぜ孤立ノートの検出をしないのか？**
ローカル化によって実現可能にはなりました。ただし運用が回る確証を得る前に機能を増やすと、使われないまま保守対象だけが増えます。必要になってから追加します。

**なぜ日次・週次の自動実行を入れないのか？**
同じ理由です。ミラー化によって自動実行は安くなりましたが、手動ループの効果を確認してから opt-in で入れる方が確実です。

**参考記事の「タグ精度 60% から 90%」という数値は根拠になるのか？**
なりません。出典は個人の投稿 1 件で、対照実験ではありません。設計の方向性としては参考にしましたが、数値を根拠にした投資判断はしていません。

**ローカルで編集した内容を Notion に戻したい**
現時点では対応していません。編集は Notion 側で行ってください。将来 push を入れる場合も、新規作成のみに限定するなど競合が起きない範囲に留める想定です。
